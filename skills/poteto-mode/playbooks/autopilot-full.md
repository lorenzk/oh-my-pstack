### Autopilot-full

**You own the verdicts and merges, never the PR implementation. One owner runs each PR through merge-ready, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program. Here owners implement their PRs, and the root owns verification, countersigns, and authorized merges.

Resolve the forge once. Default to `gh`. If `command -v origin` succeeds and Origin resolves the repository, use `origin pr`. Record a fallback to `gh`. Graphite is not required. An installed PR tool takes precedence for operations it supports, per **Opening a PR**.

1. **Mark the operator's items and honor state-then-wait.** Operator-named items stay with the operator for review and landing. A request to state the protocol or plan is not a go. State it and stop. Execution starts only on an explicit go.
2. **Start one owner per PR with an early trail.** Use canonical `owner` with the active playbook's model role. Use a fresh **Bounded session** each round by default, with the consolidated brief, prior report, and exact branch. Use **Long-lived owner** only for poteto-mode's costly live-state exception. The owner builds, pushes its assigned branch, opens a ready PR before self-proof, runs self-proof and **unslop**, and rebases before its code-ready report and Babysit. Within about 15 minutes it starts `decisions.tsv`, pushes its first snapshot, and opens the PR. Push after every verifiable unit with hooks on. Run required pre-review checks on the committed head; a hook pass is not proof. Keep the trail uncommitted and return it with reports. The root starts **no-comments** review, Babysit watchers, and other children; owners never delegate. The root records every child ID, expected runtime at least as long as past runs of that kind, state, branch, and generation in `children.tsv`. In fix rounds keep the merge base. Rebase again only at merge prep, on a `git merge-tree` conflict with trunk, or on CI failure caused by trunk drift. Publishing an authorized rebase uses `--force-with-lease` after an `ls-remote` check, never on a shared branch. Report code-ready with the shipped-code head SHA after cleanup and review fixes, then every later patch-changing push SHA. Self-proof, CI, and root-controlled Babysit run in parallel with the swarm. Report merge-ready with the exact head and receipts when they finish.
3. **Run owners in true parallel and never stack.** One writer per branch and worktree, with disjoint files. Serialize genuinely overlapping work. Independent PRs branch from trunk; sequenced work is merge-then-branch. A genuinely dependent change may use a short private stack.
4. **Swarm-verify every round before merge.** A round starts at code-ready and at every later push that changes the patch. Freeze that SHA and fan out independent verifiers through **swarm**. Run gates, a live lane on the real surface using an installed control capability or named driver, and at least two diff-audit lanes with the full brief and different primary focuses. Run a regression lane against current trunk. If trunk lacks the feature, record that and gate added behavior plus the user's end state. A verdict without the live lane is not clean. Audit merge-ready receipts before issuing the verdict. Send every proven finding in one fix-forward, including defects filed as notes. For behavior findings require a red test covering every site with that defect, or a repro receipt when no test can show it. Add the defect to the next review brief. A new patch gets a fresh swarm, except for lane results preserved by the Shipping patch-id rule.
5. **On a clean verdict the root merges and starts a fresh owner for the next item.** Merge prep follows the start of a round's lanes and ends with a rebase onto current trunk. Record the new head and require CI on it. Apply `skill://poteto-mode/playbooks/shipping.md` to decide which verdicts survive. Once the head is green and its verdict remains valid, a later trunk move alone does not require another rebase. Immediately before merge, fetch trunk, require a clean `git merge-tree` against it, and check that trunk changes since the merge base touch neither PR paths nor CI-selection config paths. If either check fails, rebase, report the new head, wait for CI, and repeat. Only the root squash-merges through the resolved forge, under the operator's landing grant and a clean verdict. Operator-named items wait for the operator. A fresh owner takes the next queue item.
6. **Run the root layer hourly.** A new raise of a pinned gate or budget requires a fresh root countersign after verifier proof. A grant covering approvals permits that countersign; record it in the tool's allowed form and have a lane check it. Never bypass forge-enforced approvals. Absorbing a value already on trunk is drift, not a raise. On go, schedule a real hourly audit through an installed host scheduler or loop facility. Native Pi has no built-in `/loop`; if no scheduler exists, record the gap and checkpoint instead of claiming unattended hourly wakes. Native child completion notifications drive result collection; do not poll or sleep to await them. At each audit re-read this playbook from trunk when it exists there, otherwise from the installed package, and the recorded objective. Probe all tracked children and owner branches. Count commits, pushes, PR or check changes, and stored reports as progress. Mark an errored or overdue lane without side effects stuck and replace it if still needed. Stop the old writer and reconcile its worktree before assigning another writer to that scope. A stall never proves or drops the work. Run retro and post-merge bot-comment sweeps after batches. Stop the scheduled tick only when no delegated work remains, even after the last merge. Log each tick; post a short status message only for tracked changes not already reported. No unchanged tables or repeated blockers.
7. **Stand down instantly on the operator's stop.** Send every active child a zero-writes order and cancel scheduled work. Preserve briefs and checkpoints until released.

**Reply:** queue with owner, state, and head SHA; each verdict and its swarm; merges and fresh next owners; countersigns and reasons; operator gates; collected trail paths.
